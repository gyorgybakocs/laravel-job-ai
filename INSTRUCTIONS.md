# Instructions

## Part 1 — Setting Up the Environment

### Why this setup?

The environment is fully containerised so that nothing is installed on your machine (or anyone else's) beyond Docker. No global PHP, Node, Composer, or Postgres. The project runs identically on every machine.

The setup may look involved at first glance, but it is well-parameterised: versions, image names, container names, ports, and credentials all live in `environment/.env.dev` and `environment/.env.secrets.dev`. Adapting it to a new project is a matter of changing those values — in practice this took roughly half an hour here.

> **Note:** A `dev` environment is fully set up. A `prod` environment (separate image targets, hardened config, no Adminer, etc.) was deliberately left out of scope for this task.

### Why a Makefile?

The Makefile wraps every Docker Compose command behind a named target with consistent `--env-file` flags. This has two benefits:

1. **Developer ergonomics** — `make provision`, `make ci`, `make up` are readable and hard to mistype.
2. **Pipeline ready** — each target maps directly to a stage in any CI/CD system (Bitbucket, GitHub Actions, GitLab CI, etc.). A deployment pipeline is essentially `make provision && make ci && make up` called from a runner. No pipeline-specific glue code is needed; the Makefile *is* the pipeline definition.

### Why three steps?

The lifecycle is split into three distinct phases because they change at different frequencies:

| Step | Command | When to run |
|------|---------|-------------|
| **Provision** | `make provision` | Once per version bump of PHP, Node, Nginx, etc. Builds all Docker images. Expensive and infrequent. |
| **CI** | `make ci` | Once per fresh checkout, or after a dependency change. Installs the official Laravel Vue starter kit and Composer dependencies, runs migrations, and builds assets. Automatically stops the running environment first. |
| **Up** | `make up` | Daily. Just starts the already-prepared containers. Fast. |

Keeping image builds separate from application setup separate from container start means you never rebuild a 500 MB image just because a migration changed.

### Why separate PHP image targets (php-base / php-dev)?

The PHP Dockerfile has two build targets:

- **`php-base`** — the production-ready base: only the extensions the application needs.
- **`php-dev`** — extends `php-base` with Xdebug for local debugging.

The separation means Xdebug never ends up in a production image. If a prod target were added, it would build from `php-base` directly, keeping the image lean and avoiding the performance overhead of having a debugger loaded in production.

### Adminer

Adminer is included as a database UI for development convenience. It is provisioned conditionally — the `provision` target only builds the Adminer image when `ENV=dev`. It does not belong in a production environment and would not be provisioned or started there.

### Redis

Redis runs without a password in the dev environment. This is intentional — there is no sensitive data on a local machine and it keeps the setup simple.

In production, Redis should be secured with `requirepass` in its configuration, and the corresponding `REDIS_PASSWORD` env var must be set in the application's `.env`. The current setup provides the hook for this: a separate `redis/Dockerfile` and Redis image are already parameterised, ready to receive a production config.

## Usage

### Prerequisites

- Docker + Docker Compose v2
- `make`

### First-time setup

```bash
# 1. Copy the environment files
cp environment/.env.dev.example environment/.env.dev
cp environment/.env.secrets.dev.example environment/.env.secrets.dev
# .env.dev works out of the box — only fill in .env.secrets.dev (POSTGRES_USER, POSTGRES_PASSWORD)

# 2. Build all Docker images
make provision

# 3. Install the application (Laravel, dependencies, migrations, assets)
make ci

# 4. Start the environment
make up
```

Add your `APP_DOMAIN` (e.g. `m-int-dev.com`) to `/etc/hosts`:

```
127.0.0.1 m-int-dev.com
```

The application is then available at `http://m-int-dev.com`.
Adminer (database UI) is available at `http://localhost:8082` (port configured via `ADMINER_PORT` in `.env.dev`).

### Day-to-day

```bash
make up        # start containers
make down      # stop and remove containers
make upd       # force-recreate containers (picks up config changes)
make restart   # restart running containers
```

### File ownership

Files created inside containers (by PHP-FPM, artisan, etc.) are owned by the container user, not the host user. This means files generated by `php artisan make:*` commands (controllers, migrations, models, etc.) will not be editable in the IDE until ownership is fixed.

Run after any artisan generator or whenever file permissions block IDE access:

```bash
make own
```

This stops the environment, resets all `app/` ownership to the host user (uid 1000), restores `storage/` and `bootstrap/cache/` permissions for PHP-FPM, then exits. Start the environment again with `make upd` when ready.

### Updating dependencies

```bash
make ci-composer   # run composer install/update
make ci-npm        # run npm install + vite build
make ci-migrate    # run pending migrations
```

### Individual provision targets

```bash
make provision-app       # rebuild PHP image
make provision-node      # rebuild Node image
make provision-nginx     # rebuild Nginx image
make provision-postgres  # rebuild Postgres image
make provision-adminer   # rebuild Adminer image
make provision-redis     # rebuild Redis image
make provision-composer  # rebuild Composer image
```

## Environment variables and the app `.env`

During `make ci`, the install script merges `environment/.env.secrets.dev` and `environment/.env.dev` into `app/.env`. This happens **once**, on first install.

> **Important:** Any subsequent changes to `environment/.env.dev` or `environment/.env.secrets.dev` are **not** automatically reflected in `app/.env`. You must update `app/.env` manually to keep them in sync.

## Part 2 — Technical Decisions

### 1. Vue and TypeScript

My previous Vue work has been with Quasar Framework and standalone Vue frontends, using Nginx `proxy_pass` to connect them to the backend. Laravel's Inertia-based starter kit is a different setup from those projects.

For this application's scope, I do not see a strong need for Vue: target forms, synchronization status, and repository browsing could be implemented with Laravel's own Blade system. PHP component classes can keep presentation logic separate from simple templates, while business logic remains in backend services. However, the task explicitly requires the official Laravel Vue starter kit, so I will use Vue and Inertia.

I would prefer to use my existing JavaScript knowledge directly in the Vue files. However, TypeScript is used throughout the official starter kit, including its shared UI components and composables. I will keep that foundation and use TypeScript rather than spend the task's time converting the frontend to JavaScript. TypeScript itself is not a requirement of the task.

I have not worked with TypeScript for approximately seven years and do not intend to use it in my future projects. Consequently, the TypeScript frontend implementation for this task will be produced entirely with AI assistance, rather than written directly using my JavaScript experience. I will review the generated code and validate its behavior through builds, relevant tests, and manual checks.

I used to be an ActionScript developer, so typed frontend code is not unfamiliar to me. Nevertheless, over the past fifteen years, nobody has convinced me that TypeScript is necessary for the projects I build. Keeping it here is a practical decision to retain the starter kit's existing structure.

### 2. PostgreSQL

Since I have already containerised the environment, running a dedicated database container is straightforward, so I chose to use it rather than SQLite. PostgreSQL is mainly a matter of familiarity: it is the database we have worked with most often over the past few years. The task does not require PostgreSQL-specific features.

This is not a production-ready implementation. For example, there is no PgBouncer connection pooler to help manage PostgreSQL's maximum connection limit as the number of application processes and queue workers grows. Production connection management and capacity planning are outside this task's scope.

### 3. Redis

In previous projects, I used Redis as a buffer in ELK pipelines and for caching. Here, I will use it as the backing store for Laravel's queue. The synchronization workflow is simple enough that I do not need RabbitMQ or AWS SQS; Redis provides a fast in-memory store with the data structures Laravel needs to enqueue and process jobs.

Redis being fast does not make the queue production-ready by itself. Persistence, availability, and worker operation would need to be configured for a production deployment. For this task, a local Redis container and Laravel's queue abstraction are sufficient.

### 4. Queue Worker Placement

The queue worker runs as a separate process alongside PHP-FPM in the existing application container. Supervisor starts and supervises both processes. The PHP image includes the Redis extension and PCNTL, and Compose waits for PostgreSQL and Redis health checks before starting the app.

A separate worker instance is unnecessary for this development workload. It would become useful if background processing needed independent scaling, resource limits, or deployment and restart control. Such an instance could reuse the PHP image and application code; no separate worker image is needed.
